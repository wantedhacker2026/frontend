# 면접 준비 기능

## 경력 항목 식별

- `경력`, `경력 사항`, `경력기술서`, `업무 경험`, `Work Experience`, `Professional Experience` 등의 제목 아래에서 수행 경험을 추출합니다.
- 자기소개·학력·교육·기술·개인 프로젝트 등 다른 항목 제목이 나오면 추출을 중단합니다. 경력 구간의 `프로젝트: 업무명`은 업무 프로젝트로 유지합니다.
- 경력 구간은 다음 페이지로 이어지지만, 문서가 바뀌거나 읽지 못한 페이지를 만나면 초기화합니다.
- 제목이 없거나 PDF 추출 과정에서 제목과 본문 구분이 사라지면 경력으로 추정하지 않습니다. `경력` 제목을 포함한 텍스트를 입력하거나 이력서를 수정해 다시 분석해야 합니다.
- JD 기준표는 서류 전체의 키워드 언급을 표시하므로, 기준표에 문장이 있어도 면접용 경력 근거가 없을 수 있습니다. `서비스 기획 직무에 관심을 갖게 되었습니다` 같은 지원 동기는 질문 근거에서 제외합니다. 생성 버튼 옆에 경력 근거 부족·검토 대기·질문지 잠금 등 비활성화 이유와 필요한 다음 행동을 표시합니다.
- 이전 질문지는 삭제하지 않고 저장 데이터를 보존합니다. 질문지 키를 `interview-career-v2`로 분리하여 예전 JD·서류 전체 기반 질문과 메모가 새 질문지에 섞이지 않게 합니다. 이전 질문지 열람 UI는 제공하지 않습니다.

## 사용 흐름

### 구직자

1. `/new-project`에서 JD와 이력서를 등록합니다. 공고만으로 생성하던 예상 면접 질문 영역은 제거했습니다.
2. 서류 분석을 마치면 `/projects/[id]/my-analysis` 상단에서 이력서의 **경력 항목에 근거한 개인별 질문 4개**를 생성한 뒤 검토 화면에서 확인합니다. 경력 근거가 없으면 질문을 생성하지 않습니다. **확인 후 질문지에 적용**을 누르면 저장됩니다.
3. 질문 이유, JD 문장, 지원서의 실제 파일·페이지·원문, 답변 준비 가이드를 확인합니다.
4. 연습 메모를 입력하고 **저장**을 누릅니다. 질문마다 준비 완료를 체크할 수 있습니다.

### 채용담당자

1. `/projects/[id]/applicants`에서 지원자를 열고 **면접 준비 → 면접 대상으로 선택 · 질문 생성**을 누릅니다. 생성 결과를 검토한 뒤 질문지에 적용합니다.
2. 선택한 지원자에 대해서만 질문을 생성합니다. 지원자 알림은 발송하지 않습니다.
3. 개인별 질문 4개는 이력서 경력 항목의 담당 업무·수행 경험만 사용합니다. JD 기반 공통 질문은 생성하지 않습니다. 경력 항목이 없으면 서류 보완 안내를 표시합니다.
4. 질문을 수정·저장, 이동, 삭제할 수 있습니다. 직접 수정한 질문은 ‘직접 수정’으로 표시됩니다.
5. **질문지 확정 → 면접 완료로 표시**로 진행하고, 필요하면 다시 준비 상태로 열 수 있습니다.
6. 면접관 메모와 ‘아직 질문 전 / 구체적 사례 확인 / 일부 확인 / 추가 확인 필요’를 별도로 저장합니다.
7. 질문·메모 복사 또는 인쇄용 보기로 내보냅니다. 인쇄용 출력은 HTML을 해석하지 않고 일반 텍스트로 표시합니다.

### 추출 경력과 원문 확인

- 채용담당자의 **면접 준비 → 이력서에서 추출한 경력**에서 질문 후보로 추출한 경력 원문을 먼저 확인합니다. 추출한 근거 수와 현재 질문지에 연결된 근거 수를 표시하며 후보는 최대 12개입니다.
- 각 근거에 파일명·페이지와 연결된 질문 번호·제목·질문 의도를 표시합니다. 같은 원문에서 여러 질문이 생성되면 한 근거 아래에 함께 모읍니다. 질문을 이동·삭제하면 현재 질문지 순서와 연결 상태를 반영합니다.
- 연결된 질문을 누르면 해당 질문 카드로 이동합니다. 아직 질문을 생성하지 않았거나 현재 질문에 사용하지 않은 후보도 확인할 수 있습니다. 적용 전 생성 결과는 **새로 생성된 질문 검토**에서 별도로 확인합니다.
- **원문 페이지 보기**를 누르면 저장된 해당 페이지의 추출 텍스트 전체를 열고 근거 문장 위치로 이동해 강조합니다. PDF 원본 이미지 뷰어는 아니며, 문서에서 추출·저장된 텍스트를 보여줍니다.
- 질문 카드와 생성 결과 검토 화면의 경력 근거는 접지 않고 바로 표시합니다. 실제 문서·지원자·페이지·원문 일치를 다시 확인하며, 다른 지원자 문서나 읽지 못한 페이지, 원문에 없는 인용은 표시하지 않습니다.
- 추가 AI 호출 없이 기존 경력 추출 결과와 저장한 질문을 연결합니다. 메모와 질문을 새로 생성할 필요 없이 근거 표시를 사용할 수 있습니다.

질문 재생성은 명시적 버튼으로만 실행합니다. 직접 수정한 질문, 기존 순서, 삭제한 질문의 제외 상태, 저장한 메모는 유지합니다. 질문 문구가 바뀌면 해당 질문의 준비/확인 상태는 초기화합니다. 질문 전체를 다시 구성하려면 새 분석 회차를 사용합니다.

## 생성 결과 검토

### 지원서 경험에서 개인화 주제 추출

- `lib/interview/experiences.ts`에서 선택한 지원자의 읽을 수 있는 문서 페이지를 문장·줄 단위로 나눕니다. JD 분석에서 매칭되지 않은 경험도 대상입니다.
- 구현·설계·개선·기획·조율·운영 등 수행 표현이 있는 문장을 규칙으로 추출합니다. 기술명 나열, 단순 희망·예정, 경험 부재 표현과 일부 개인정보 패턴은 제외합니다. 이는 의미를 완전히 이해하는 AI 추출이나 완전한 개인정보 제거 기능이 아닙니다.
- 같은 문장은 중복 제거하고, 구체적 행동·수치가 있는 문장을 우선합니다. JD 관련성은 보조 기준이며 JD만으로 개인화 주제를 만들지 않습니다. 후보는 최대 12개, 질문에 사용하는 경험은 최대 4개입니다.
- 추출 후보의 내부 이름은 문장 앞부분이지만, 화면 제목은 AI가 질문과 함께 만든 짧은 업무명(권장 10~25자, 최대 30자)으로 표시합니다. 기본 질문은 역할·진행·협업·결과 확인 제목을 사용합니다. 원문·파일·페이지는 별도로 보존합니다.
- 각 질문에 경험 ID와 근거 ID를 붙여 Kotlin API로 전달합니다. AI가 제목·질문 의도·주 질문·후속 질문·준비 가이드를 함께 작성하고 사용한 근거 ID를 반환합니다. 화면의 원문과 출처는 해당 경험의 실제 자료에서만 연결합니다.
- 경력 항목에서 구체적인 업무 경험을 찾지 못하면 AI를 호출하지 않고 질문 0개와 서류 보완 안내를 표시합니다. 문서 추출의 한계이며 지원자의 역량 부족을 뜻하지 않습니다.
- 기존에 저장한 질문은 자동 변경하지 않습니다. **질문 다시 생성 → 검토 → 적용**으로 반영하며 직접 수정한 질문과 메모 보존 규칙은 유지됩니다.

### 제목과 근거의 맥락 검증

1. 코드 검사: 입력 질문 ID, 경험 ID, 해당 경험의 근거 ID, 중복 ID, 제목 길이·줄바꿈, 필수 문장 등을 확인합니다. 다른 경험의 근거와 생성된 출처는 사용할 수 없습니다. 생성 결과에 쓰인 영문 기술명·약어와 숫자가 선택한 근거 원문에 등장하는지도 검사합니다. JD에만 있는 표현은 허용하지 않으며 대소문자와 숫자 쉼표는 정규화합니다.
2. 별도의 AI 검토: 생성에 사용한 JD·사용자 지침을 제외하고 **선택한 근거 원문과 생성 결과만** 전달합니다. 제목·주 질문·후속 질문·답변 가이드·질문 의도가 같은 업무를 다루는지, 없는 기술·사건·수치를 사실로 전제하는지 검사합니다.
3. 실패한 질문만 한 번 재생성하고 다시 검사합니다. 이미 통과한 질문은 유지합니다. 검토 결과 누락·오류·시간 초과도 통과로 취급하지 않습니다.
4. 두 번째에도 통과하지 못하면 해당 업무의 담당 범위·진행을 묻는 기본 질문으로 대체합니다. 질문마다 **AI 질문 · 맥락 자동 검토 / 기본 질문**을 표시하고, 혼합 결과에서는 각각의 개수를 안내합니다.

생성 1회와 검토 1회가 기본이며 재시도 시 최대 4회 호출합니다. 공급자 호출당 최대 20초, 전체 50초를 공유합니다. Next.js의 서버 연결 제한은 55초, 실행 제한은 60초, 브라우저 요청 제한은 65초입니다. 추가 검토 때문에 기존보다 시간·비용이 증가할 수 있습니다.

맥락 검토는 AI 판단이므로 완전한 정확성을 보장하지 않습니다. 질문과 원문을 함께 검토한 뒤 적용해야 합니다. 경력 추출은 여전히 문장·줄 단위이며 회사·프로젝트 전체를 묶는 의미 기반 추출은 포함하지 않습니다.

새 요청에는 `experienceId`와 `evidenceIds`가 필수이며 프론트엔드·서버를 함께 배포해야 합니다. 버전이 다른 동안은 근거 연결·검토 정보를 확인할 수 없어 기본 질문으로 대체됩니다. 기존 저장 질문과 메모는 유지하고 재생성한 결과를 검토·적용할 때만 바꿉니다.

### 검토와 적용

1. **질문 생성 / 질문 다시 생성**을 누르면 새 결과를 별도로 생성합니다. 저장된 질문은 그대로 유지합니다.
2. **새로 생성된 질문 검토** 화면에서 AI/기본 질문 구분, 요청한 지침, 질문 이유와 JD·지원서 근거, 후속 질문과 준비 가이드를 확인합니다.
3. 재생성한 결과는 기존 질문과 나란히 표시합니다. 새 질문, 변경 예정, 기존과 동일, 직접 수정한 질문 유지, 삭제한 질문 적용 제외를 구분합니다.
4. **확인 후 질문지에 적용**을 누르면 검토한 결과를 저장합니다. 직접 수정한 질문, 기존 순서와 메모, 삭제 상태는 유지합니다. 질문 문구가 바뀐 항목의 준비/확인 상태는 초기화됩니다.
5. **취소 · 기존 질문 유지**를 누르면 생성 결과만 버립니다. 창을 닫기만 하면 **생성 결과 확인** 버튼으로 다시 열 수 있습니다.
6. 분석 후 생성한 검토 결과는 소유자·프로젝트·분석 회차별로 현재 탭의 `sessionStorage`에 임시 저장합니다. 같은 탭의 새로고침에도 유지되며 다른 계정·지원자 결과와 섞이지 않습니다.
7. 검토 중 기존 질문·메모 또는 면접 단계가 변경되면 적용을 막습니다. 결과를 취소하고 최신 상태에서 다시 생성해야 합니다.

AI 요청 실패로 생성된 기본 질문도 명확하게 표시하며, 검토 전에 기존 AI 질문을 덮어쓰지 않습니다. 프롬프트 자체의 저장과 질문 적용은 별개입니다.

## 저장과 경계

- 기존 브라우저 저장소 `wantedhacker-projects-v1`의 프로젝트에 선택 필드 `interviews`를 추가했습니다. 과거 데이터는 그대로 읽습니다.
- 질문 묶음은 `interview-v1:revisionId:analysisId`로 구분합니다. 재방문은 저장한 묶음을 사용하고 재분석은 새로운 묶음을 생성합니다.
- 소유자·역할·분석 회차·지원자 분석 ID를 검사하고, 묶음 버전으로 오래된 화면의 덮어쓰기를 거부합니다.
- 재분석 저장과 면접 메모 저장이 겹쳐도 최신 면접 메모를 보존합니다. 면접 기능은 서류 분석 결과나 점수를 변경하지 않습니다.
- 구직자 연습 메모와 채용담당자 질문·메모는 서로 다른 소유 프로젝트에 저장됩니다. 생성 요청에는 점수, 배점, 이름, 생년월일 및 메모 필드를 넣지 않습니다. 원문 자체에 개인정보가 포함되어 있다면 관련 발췌문에 포함될 수 있습니다.
- 현재는 **브라우저 로컬 데모**입니다. 화면상의 역할 분리는 실제 서버 인증/인가나 기기 간 동기화를 제공하지 않습니다. 같은 브라우저 저장소에 접근 가능한 사람에게서 데이터를 보호하는 보안 경계가 아닙니다.

## AI 연결과 키 관리

호출 경로: 브라우저 → Next.js `/api/interviews` → Kotlin `/api/interviews` → OpenAI Responses API.
OpenAI API 키·모델·기본 시스템 프롬프트는 Kotlin 백엔드에서만 관리합니다. 웹 컨테이너에는 OpenAI 키를 전달하지 않습니다.

백엔드 저장소 `../03_wantedhacker-server/.env`:

```dotenv
OPENAI_API_KEY=<API 키>
OPENAI_INTERVIEW_MODEL=gpt-4.1-mini
INTERVIEW_AI_ENABLED=true
INTERVIEW_PROXY_SECRET=<32자 이상의 임의 값>
```

프론트엔드 저장소 `.env`:

```dotenv
WANTEDHACKER_SERVER_URL=http://127.0.0.1:8080
INTERVIEW_PROXY_SECRET=<백엔드와 같은 임의 값>
SESSION_COOKIE_SECURE=false
```

로그인은 서버의 이메일 인증 코드를 사용합니다. HTTPS 배포 시 `SESSION_COOKIE_SECURE=true`를 사용합니다. SMTP 설정과 로컬 테스트 메일함은 [이메일 인증 문서](email-auth.md)를 참고하세요.

Docker Compose가 백엔드 `.env`를 서버에 주입합니다. 소스 변경은 `docker compose up --build -d --wait web`, 환경값만 변경하면 `docker compose up -d --force-recreate --wait server web`으로 적용합니다. Docker 밖에서 Kotlin을 실행할 때는 같은 값을 서버 프로세스 환경변수로 별도 주입해야 합니다.

- Next.js는 HttpOnly 세션과 요청 역할을 확인하고 백엔드에 access token을 전달합니다. 백엔드는 JWT와 면접 프록시 공유 비밀 값을 검사합니다.
- 기존 데모 로그인은 허용하지 않습니다. 이메일 인증으로 다시 로그인해야 하며 비밀번호는 사용하지 않습니다.
- 홈의 프로젝트 생성 링크와 `/new-project` 직접 접근 모두 비로그인 시 `/login?next=...`로 이동합니다. 로그인 성공 후 원래 프로젝트 생성 화면으로 돌아옵니다.
- [공식 Structured Outputs 형식](https://developers.openai.com/api/docs/guides/structured-outputs)을 사용하며 `store: false`를 적용합니다. 형식 일치만으로 의미적 정확성이 보장되지 않으므로 코드 검사와 별도 맥락 검토를 수행합니다.
- 원문·파일·페이지는 모델 응답에서 받지 않고 근거 ID로 기존 자료에서 연결합니다. 제목과 질문 이유는 질문과 함께 생성·검토합니다.
- 구직자와 채용담당자 모두 경력 기반 개인별 질문 4개만 AI로 생성합니다.
- JD 입력 중에는 질문을 생성하지 않습니다. 경력 내용이 포함된 이력서 분석 후 질문을 생성하고 검토·적용합니다.
- 키 미설정·요청 실패·거부·시간 초과·형식 오류 시 기본 질문임을 표시합니다. AI 성공으로 표시하지 않습니다.
- 웹과 백엔드 각각 프로세스당 분당 20회/동시 3회를 제한합니다.
- 프로젝트와 면접 메모는 여전히 브라우저 저장소입니다. 이메일 소유 인증은 연결했지만, 공개 서비스의 서버 프로젝트 소유권 검증·공유 요청 제한·DB 저장은 별도 구현이 필요합니다. 채용 조직 소속 확인과 권한 관리는 이메일 인증과 다릅니다.

## 프롬프트 관리

### 자연스러운 면접 질문 표현

- 주 질문은 한 문장으로 한 가지를 묻고, 가능하면 80자 이내로 작성하도록 백엔드 시스템 지침을 구성했습니다.
- 원문 전체를 질문에 반복 인용하지 않고 필요한 기술명·작업 내용만 짧게 언급합니다. 전체 근거는 기존 파일·페이지·원문 표시에서 확인합니다.
- 역할·대안·해결 과정·성과를 한꺼번에 묻지 않고 후속 질문 1~~2개로 나눕니다. 답변 준비 가이드도 1~~3개의 짧은 안내로 요청합니다. 기존 API 허용 범위는 유지합니다.
- 사용자 추가 지침은 경험에 관련될 때만 반영합니다. 협업·기획 질문에 장애나 재발 방지를 일괄 적용하지 않고, 근거 없는 사건을 전제로 질문하지 않도록 명시했습니다.
- AI를 호출하지 못할 때의 기본 질문도 짧은 주 질문과 관점별 후속 질문으로 변경했습니다. 개인화 기본 질문의 ‘이 경험’은 같은 카드의 경험 주제와 원문을 가리킵니다.
- 현재 모델 `gpt-4.1-mini`를 유지합니다. 길이와 말투는 생성 지침이므로 결과 검토는 필요합니다.

### 프로젝트별 지침 저장

- 프로젝트 생성 화면의 **면접 질문 생성 지침 (프롬프트)**에 확인할 역량·난이도·질문 방식을 2,000자 이내로 입력합니다.
- 면접 준비 화면의 **질문 생성 지침 관리**에서 수정한 뒤 **지침 저장** 또는 **질문 다시 생성**을 누릅니다. 재생성 시 지침도 함께 저장합니다.
- 비워두고 저장하면 기본 지침으로 돌아갑니다. 저장만 하면 기존 질문은 바뀌지 않습니다.
- 프로젝트별 `interviewPrompt`로 저장하고 각 질문지에 `promptUsed`를 기록해 실제 사용한 지침을 확인합니다. 예전 질문지의 지침은 기록이 없을 수 있습니다.
- 직접 수정한 질문, 순서, 삭제 상태, 메모는 재생성해도 보존합니다.
- 백엔드 공통 지침은 `src/main/resources/interview/system-prompt.txt`에서 관리합니다. 사용자 프롬프트는 별도 입력 데이터로 전달하며 공통 원칙·출력 형식을 교체하지 않습니다.
- 맥락 검토 지침은 `src/main/resources/interview/grounding-review-prompt.txt`에서 관리합니다. 생성 결과를 믿거나 지침을 수행하지 않고 각 필드와 근거의 일치 여부만 판정합니다.
