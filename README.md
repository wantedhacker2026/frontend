# Shortlist

**지원서를 읽는 시간은 줄이고, 더 좋은 채용 결정에 집중하세요.**

JD 정량 평가표를 중심으로 채용담당자의 빠른 비교와 지원자의 구체적인 다음 행동을 연결하는 실행 가능한 프론트엔드 MVP입니다. 화면 목업이 아니라 공고 등록, 평가 기준 편집, 지원, 재평가, 검토 상태 저장까지 동작합니다.

## 빠르게 실행하기

Node.js 22를 사용하세요. 개발, 빌드, 배포의 Node.js 버전을 22로 통일했습니다.

```bash
npm ci
npm run dev
```

[http://localhost:3000](http://localhost:3000)에서 시작합니다. 계정, 환경 변수, Supabase 설정, API 키가 필요하지 않습니다.

```bash
npm run build
npm start
```

프로덕션 빌드는 `next build --webpack`을 사용합니다. 개발 서버는 Turbopack을 사용합니다. 제한된 실행 환경에서 Turbopack의 빌드 프로세스 통신 오류가 발생해, 검증 가능한 Webpack 빌드를 기본값으로 선택했습니다.

## 해결하는 문제

- 채용담당자: 지원서 원문을 하나씩 열기 전에 동일 기준의 점수·필수조건·강점·확인할 부분을 비교합니다.
- 지원자: 평가를 합격·탈락 통보로 받아들이는 대신, 근거가 부족한 부분과 실천 방법을 확인합니다.
- 양쪽 모두: 점수를 단독 판단 기준으로 사용하지 않고 지원서에서 확인된 근거를 함께 봅니다.

## 체험 흐름

### 채용담당자

1. 랜딩에서 **채용담당자로 체험하기**를 선택합니다.
2. 채용 대시보드 → Backend Engineer → 지원자 목록으로 이동합니다.
3. 이름/기술 검색, 점수, 필수조건, 기술 스택, 경력, 검토 상태 필터를 사용합니다.
4. 점수 높은 순·최근 지원순·이름순으로 정렬합니다.
5. 체크박스로 2~3명을 선택하고 **지원자 비교**를 누릅니다.
6. 상세 평가의 각 항목을 펼쳐 원문 근거를 확인합니다. 지원서 전체 원문은 기본적으로 접혀 있습니다.
7. 검토 전·검토 완료·면접 검토 상태를 변경합니다. 새로고침 후에도 유지됩니다.
8. **새 채용공고**에서 JD를 작성하고 기준을 생성합니다. 배점 합계가 100이 아니면 저장을 차단합니다.
9. 기존 공고의 **평가 기준**을 수정하면 모든 지원서를 다시 평가하며 검토 상태와 액션 완료 기록을 초기화합니다.

### 지원자

1. 랜딩에서 **지원자로 체험하기**를 선택합니다.
2. **내 지원서**에서 이름을 붙인 버전을 여러 개 저장합니다. 예시를 채워 시작하거나 기존 버전을 복제·수정할 수 있습니다.
3. 채용공고 탐색 → Backend Engineer → **지원하고 분석받기**에서 저장한 버전을 선택합니다. 또는 새로 작성해 **버전만 저장**, **버전 저장 후 지원·분석**을 선택합니다.
4. 제출하면 사용한 버전 이름과 수정 번호, 종합 매칭 점수, 카테고리별 충족도와 강점을 확인합니다. 저장 원본을 나중에 수정·삭제해도 제출 당시 내용과 분석 결과는 유지됩니다.
5. **나의 다음 단계**에서 우선순위에 따른 Gap → Reason → Action을 확인합니다.
6. 추천 CTA를 누르면 가상 프로젝트·학습·자격증·인턴십의 상세 가이드가 열립니다.
7. 완료 체크로 실천 기록을 남깁니다. 체크만으로 점수를 올리지 않습니다.
8. **지원서 보강하기**에서 실제 경험을 추가하고 다시 분석합니다. 같은 지원서를 갱신하며 중복 지원서를 만들지 않습니다.

샘플 결과는 `/applications/application-4`에서 바로 확인할 수 있습니다. **내 지원 현황**에는 해당 브라우저에서 직접 작성하거나 수정한 지원서가 표시됩니다.

## 기본 데이터

총 3개 공고, 20명 지원자, 20개 지원서, 20개 평가를 제공합니다.

| 공고 ID    | 공고              | 지원서 |
| ---------- | ----------------- | -----: |
| `backend`  | Backend Engineer  |     12 |
| `frontend` | Frontend Engineer |      4 |
| `data`     | Data Engineer     |      4 |

지원자마다 경력, 기술, 프로젝트, 협업 경험이 다릅니다. 종합 점수는 하드코딩하지 않고 실제 Seed 지원서를 평가해 계산합니다. Strong / Good / Partial / Low Match가 모두 나오도록 구성했습니다. 랜딩의 작은 제품 미리보기는 명시된 화면 예시입니다.

사이드바의 **데모 이용 가이드 → 데모 데이터 초기화**에서 초기 20개 지원서로 돌아갈 수 있습니다. 초기화 확인창이 제공됩니다.

## 서비스 구조와 기술

```text
JD 작성 → 기준 생성 및 수정 → 100점 검증
                            ↓
지원서 작성 → CandidateEvaluator → Evaluation + ImprovementAction
                                  ├─ 채용담당자: 배점, 항목 점수, 근거, 비교표
                                  └─ 지원자: 종합 점수, 역량 상태, 근거, 개선 계획
```

- Next.js 16 / React 19 / App Router
- TypeScript strict
- Tailwind CSS 4 + CSS 기반 디자인 시스템
- shadcn/ui 구성 방식의 Button, Radix Dialog, CVA, `cn` 유틸리티
- lucide-react 아이콘
- React Context / state, 브라우저 `localStorage`
- Zod 저장 데이터 검증
- Node Test Runner + tsx, ESLint, Prettier

외부 폰트, 이미지, AI 서비스가 없어도 설치 후 모든 핵심 흐름이 실행됩니다. DB 및 AI 요청은 요구사항에 따라 이번 범위에서 연결하지 않았습니다.

## Match Score 계산

각 평가 기준은 `category`, `name`, `description`, `keywords`, `weight`, `required`를 갖습니다. JD에 알려진 키워드가 등장하면 템플릿에서 기준을 생성하고 합계를 100으로 정규화합니다. JD의 지원 자격/우대사항 구역을 구분합니다. 인식하지 못한 역량은 편집기에서 직접 추가할 수 있습니다. 생성 결과는 반드시 담당자가 확인하는 초안입니다.

키워드는 영문 단어 경계를 확인하므로 `JavaScript`를 `Java` 경험으로 평가하지 않습니다. 빈 키워드는 무시하고 단순 반복으로 점수를 올리지 않습니다.

| 지원서의 근거                             | 항목 비율 |
| ----------------------------------------- | --------: |
| 직접 구현/설계/운영 + 수치 또는 운영 결과 |      1.00 |
| 직접 구현/설계/운영 경험                  |      0.85 |
| 관련 문장만 있음                          |      0.55 |
| 기술 스택에만 기재                        |      0.45 |
| 학습·강의·예정·튜토리얼                   |      0.35 |
| 근거 없음 또는 명시적인 미경험            |      0.00 |

```text
항목 점수 = round(근거 비율 × weight, 소수 1자리)
종합 점수 = round(모든 항목 점수의 합)
카테고리 충족도 = round(카테고리 항목 점수 합 / 배점 합 × 100)
필수조건 충족 = 모든 required 항목의 득점 비율이 0.65 이상
```

- 이름, 이메일, 지원동기는 점수에 반영하지 않습니다.
- 프로젝트 항목은 프로젝트 입력란, 협업 항목은 협업 입력란의 근거만 사용합니다.
- 경력 연수는 별도 검토 정보입니다. 점수에 중복 가산하지 않고 권장 연수보다 짧으면 경험 확장 액션을 제공합니다.
- 85점 이상 Strong Match, 70~~84 Good Match, 50~~69 Partial Match, 50 미만 Low Match입니다.
- 모든 항목은 실제 지원서 문장의 `evidence` 또는 근거가 확인되지 않았다는 `reason`을 갖습니다.
- 0.65 미만 항목에는 개선 액션을 생성합니다. 예상 증가량을 기준으로 우선순위를 정하며 점수 상승을 보장하지 않습니다.
- 키워드 방식은 문맥, 부정 표현의 범위, 성과의 진위, 직무별 난이도를 충분히 이해하지 못합니다. 실제 자동 선발/탈락 판단에 사용하기 위한 모델이 아닙니다.

## 향후 AI Evaluation 교체

`CandidateEvaluator`는 `EvaluationResult | Promise<EvaluationResult>`를 반환합니다. 지원서 제출과 기준 재평가 사용 사례는 이미 비동기 결과를 기다리고 오류를 표시합니다.

1. 서버에 JD·기준·지원서를 전달하는 평가 API를 구현합니다. API 키는 서버에만 둡니다.
2. `CandidateEvaluator`를 구현하는 API 어댑터를 추가합니다.
3. `lib/store.tsx`의 평가기 주입 지점을 해당 어댑터로 교체합니다. Seed 초기화는 동기 `MockCandidateEvaluator`를 유지할 수 있습니다.
4. 응답의 점수 범위, 기준 ID, 배점, 원문 인용 일치 여부를 검증하고 도메인 `EvaluationResult`로 변환합니다.
5. 평가 대기/실패/재시도 상태와 모델·프롬프트·기준 버전을 서버에 기록합니다.

화면은 평가기의 구현이 아닌 도메인 결과에 의존합니다. 추천도 `ActionType`과 `links.resourceType`으로 연결되어 실제 추천 API로 교체할 수 있습니다.

## 데이터 저장 및 현재 범위

`localStorage` 키는 `shortlist-demo-v1`입니다. 공고, 지원서 버전, 제출 내역, 평가, 검토 상태, 개선 액션 완료 기록을 저장합니다. 저장 구조는 v2이며 기존 `shortlist-demo-v1` 키를 유지해 v1 데이터를 자동으로 이전합니다. 이전에 직접 제출한 유효한 지원서만 재사용 버전으로 가져오며, Seed 지원자 20명은 내 지원서로 가져오지 않습니다. 기존 제출 내역과 점수는 유지됩니다. 저장소가 차단되거나 데이터가 손상되면 안내 메시지를 표시하고 데모를 계속 사용할 수 있습니다. 지원서 버전 저장·복제·삭제와 지원 제출은 저장 실패 시 완료 처리하지 않고 재시도 안내를 표시합니다. 다른 데모 작업의 쓰기 실패 시에는 새로고침 후 변경이 사라질 수 있음을 알립니다.

이 버전은 **한 브라우저에서 체험하는 프론트엔드 데모**입니다.

- 역할 선택은 Mock Login이며 인증·인가가 아닙니다.
- 내부 배점은 지원자 UI에 렌더링하지 않습니다. 프론트엔드 번들과 브라우저 저장소에는 전체 데모 데이터가 있으므로 실제 기밀 보호 경계가 아닙니다.
- 여러 탭의 동시 수정, 기기 간 동기화, 다중 기업 격리는 구현하지 않았습니다.
- 실제 개인정보를 수집하거나 기업에 전송하지 않습니다.
- 실제 결제, 이메일, 메시징, OCR, 기업 인증, ATS, 자격증/인턴십/프로젝트 API는 포함하지 않습니다.
- 추천은 명시된 Mock 예시입니다. CTA는 상세 가이드나 지원서 보강 화면으로 연결됩니다.

서버/Supabase를 연결할 때는 역할별 응답 모델과 DB 권한 정책으로 내부 배점을 분리하고, 기업·지원자별 접근 제어를 서버에서 적용해야 합니다. 프론트엔드에서 요소를 숨기는 것만으로 권한을 처리하면 안 됩니다.

## 검증

```bash
npm test
npm run typecheck
npm run lint
npm run build
npm run format:check
```

단위 테스트 24개는 버전 저장·복제·수정의 독립성, 선택한 버전의 평가 반영, 원본 삭제 후 제출 기록 보존, 기존 데이터 이전, Seed 일관성, 점수 범위, 필수조건, 100점 검증, 단어 경계, 부정 표현, 학습/실무 구분, 반복 키워드, 근거 입력란 분리, 저장 데이터 손상을 확인합니다.

브라우저 검증 내용과 재현 절차는 [docs/verification.md](docs/verification.md)에 기록합니다.

## 확장 방향

- Supabase/PostgreSQL 영속 저장과 실제 인증, 기업 단위 권한 분리
- 서버 측 평가 큐·재시도·기준 버전 관리·감사 기록
- LLM 근거 추출과 검증, 담당자의 항목별 수정과 피드백
- 이력서 업로드 → 정규화된 `ApplicationInput` 변환
- 출처와 최신성을 확인하는 실제 학습·프로젝트·인턴십 추천
- 평가 편향, 채용 성과, 지원자의 개선 행동을 검증하는 측정 체계

- `prod`: 검증한 배포 기준 코드를 보관하는 기본 브랜치입니다.
- `dev`: 기능 개발과 수정 사항을 통합하는 개발 브랜치입니다.
- 초기 두 브랜치는 동일한 MVP 커밋에서 시작합니다. 이후 `dev`에서 검증한 변경을 PR로 `prod`에 반영합니다.
- 브랜치 생성만으로 서버 배포가 실행되지는 않습니다. 실제 호스팅과 환경별 API 연결은 별도 설정합니다.

## 구현 참고

라우팅과 Server/Client 경계는 [Next.js 공식 문서](https://nextjs.org/docs/app/getting-started/server-and-client-components), UI 구성은 [shadcn/ui 수동 설치 안내](https://ui.shadcn.com/docs/installation/manual)를 참고했습니다.

## 지원서 버전 관리

- `/resumes`: 저장된 지원서 목록, 복제, 수정, 삭제, 공고 선택 후 지원
- `/resumes/new`: 새 버전 작성. 제출한 내 지원서에서도 새 버전을 만들 수 있습니다.
- `/resumes/[resumeId]/edit`: 현재 버전 갱신 또는 별도 버전으로 저장
- `/jobs/[jobId]/apply?resumeId=...`: 특정 버전을 미리 선택한 지원 화면

`ResumeVersion`은 제목, 입력 내용, 수정 번호와 생성·수정 시간을 갖습니다. 제출 시 이름·이메일과 경험 내용을 별도 Candidate/Application으로 복사하며 `resumeSource`에 당시 버전 이름과 수정 번호를 남깁니다. 저장 원본 삭제 후에도 이 기록은 남습니다. 결과 화면에서 명시적으로 기존 지원서를 보강해 재분석하면 원본 버전은 바뀌지 않으며, 수정된 제출 내역의 이전 버전 표시는 제거됩니다.

운영 주소는 [wantedhacker.store](https://wantedhacker.store)입니다. GitHub `wantedhacker2026/frontend`의 `prod` 코드를 Vercel `wantedhacker-frontend` 프로젝트에 직접 배포합니다. GitHub 앱의 조직 저장소 접근 권한이 없어 자동 배포 연결은 별도 설정이 필요합니다.

## Framer 서류 분석 시안 적용

- 공통 워크스페이스에 파란색 프로젝트 탐색 메뉴를 적용했습니다. 지원자는 공고별 최신 제출 결과 또는 공고 상세로 이동합니다.
- 지원자 분석과 채용담당자 상세에 실제 JD 기준으로 구성한 핵심 키워드와 근거 중심 분석표를 제공합니다.
- 전체 / 근거 확인 / 보완할 항목으로 필터링하고, JD 항목을 클릭하면 요구사항·분석 이유·제출 원문을 모달로 확인합니다. 지원자는 해당 항목의 개선 가이드로 이어집니다.
- 모바일에서는 분석표를 카드 형태로 표시합니다. 내부 배점은 채용담당자 화면에서만 표시합니다.
- `components/evaluation/jd-brief.tsx`, `document-analysis.tsx`, `app/workspace.css`로 화면 구성과 스타일을 분리했습니다.
- 적용 범위는 선택된 서류 분석 화면, 연결된 상세 모달, 공통 프로젝트 탐색입니다. 시안의 JD URL 수집·이미지/PDF 업로드·AI 인터뷰는 연동하지 않았으며 기존 지원서 버전 선택·텍스트 수정·데모 분석을 사용합니다.
